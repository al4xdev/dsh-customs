# Companion Android14 — Kotlin/Compose/Material 3

## Pré-condição e objetivo
Usar o goal ativo para guiar a fase nativa. A prova técnica do conceito foi concluída nas tasks40/45/47: frontend publicado, confirmação nativa, autenticação, histórico/reconexão, tool real e descoberta completa880sessões com writer distinto de controle. Há uma limitação explícita: terminais existentes sem bridge não recebem mensagens; não reiniciá-los ou hot-injetar módulos.

Portar o CLIENTE do companion para Kotlin nativo, exclusivamente Android14/API34, com Jetpack Compose e Material3. Não investir em React/animações. O DSH/backend de observação permanece no PC, pois observa/controla as sessões desse PC; não afirmar que o motor DSH/LLM estará rodando no Android. O objetivo de simplificação é retirar a necessidade do frontend/proxy React separado quando o cliente nativo estiver validado.

## Etapas
1. Auditar ambiente Android/JDK/Gradle/SDK34 disponível, sem ler/expor chaves de outros apps, instalar APK em celular ou alterar projetos existentes. Inspecionar contratos públicos DSH0.2.0-rc.2: auth, RPC, remote.mux, retenção/follow/page/projections, queue/cancel e approval. Mapear DTOs Kotlin estritos e limites; nenhuma adivinhação de mensagens ou dependência de internals privados.
2. Resolver a listagem exclusiva companion antes de reter chats: summary nativo não contém agentPreset. Preferir uma pequena extensão host somente no backend companion, usando APIs públicas de remotes/auth e sessionPersistence.list/stat para devolver metadados validados, reutilizando lógica/catalog guards. Sem novo daemon, backend arbitrário, registro global de tools, firewall RPC fictício ou edição do runtime instalado. Se não houver seam pública autenticada adequada, documentar e manter proxy atual até alternativa segura; não publicar endpoint aberto.
3. Criar projeto Android próprio, por exemplo android/companion, package exclusivo. minSdk34/targetSdk34, Kotlin/Compose/Material3, build reproduzível e lint/testes adequados. Não WebView, iframe, React renderer, TUI fork ou dependência do app CasaTequila. Reutilizar contratos/semântica DSH, não alegar reutilização do renderer React no Compose.
4. UI mínima lista/chat, Novo, Back, estado de conexão, composer/enviar/cancelar, histórico paginado e resposta streaming. Sem seleção de profile/modelo, configurações do DSH ou editor/terminal. Markdown/código/tabelas e resultados de tools com fallback textual seguro. Motion somente padrões do Material/OS, sem novo investimento premium.
5. Autenticação HTTPS no origin fixo proprietário, token de inicialização apenas em memória durante login, redirecionamentos e cookies validados, sem logs/interceptors/HAR/clipboard/build secrets. Persistir cookie somente se necessário em storage cifrado via Android Keystore; não armazenar startup token. TLS padrão, sem trust-all ou bypass. Sem anexar perfil pessoal de browser.
6. Somente criar/abrir/reter chats companion após prova de header/preset e revalidar corrida/deep links. Preservar API autenticada de OWNER e caveat de confiança. Seleção de outra sessão para observar/enviar continua sendo a tool session dentro do chat, não montagem de agentes normais pelo app.
7. Aprovações nativas: mostrar destino/ação/texto literais, Rejeitar/Permitir uma vez, estado esperando e respostas idempotentes. Nunca autoaprovar, decidir pelo usuário, confundir ACK com execução concluída ou repetir resultado desconhecido. Dados de logs são texto não confiável.
8. Testar parser/protocolo com fixtures sintéticas e NativeAPI real read-only; erros/timeouts/reauth, ordem/replay de streaming, paginação, reload/reconnect, selection/copy, keyboard/insets Android14, aprovação/rejeição só com alvo sintético. SDK/emuladorAPI34 se disponível; não afirmar teste físico se não realizado. Não instalar/iniciar apps no celular pessoal sem confirmação específica.
9. Gerar APK de teste, inspecionar package/minSdk/targetSdk e entregar arquivo existente via present. Não reutilizar signing keys de outro app. Documentar como usar/login/limites e manter Web/TUI/proxy funcionando como rollback. Somente desativar frontend3082 ou mover8443->3081 após validação do APK e autorização de publicação correspondente; não mudar443/3080 nem perfis/modelos/históricos de terceiros.

## Aceite
APK nativo compilado/checado para API34 com lista/chat/streaming/history/confirmations seguros e evidências reais ou limites explicitamente reportados. Backend único no PC, sem daemon frontend adicional necessário na arquitetura final validada. Web/TUI existentes e políticas companion preservados; nenhum segredo em código/artifacts/logs, nenhum envio a sessões reais para testar, nenhum takeover. Sem commit/push.
