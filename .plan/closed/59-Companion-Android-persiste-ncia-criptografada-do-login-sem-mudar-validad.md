# Android 14 Companion persistent login

## Request and confirmed contract
Owner wants to avoid pasting the link on every launch, PC reboot, or short interval. DSH rc.2 uses a per-process launch token and signed cookie backed by a persistent secret in credentials; `cookieMaxAgeDays` is a finite positive integer, default 30. A valid cookie can survive a PC reboot. The current client loses all cookies when its process terminates. The owner requested to proceed.

## Authorized scope of this revision
1. Store only valid owner cookies, encrypted using AES-GCM and a non-exportable Android Keystore key, in a private directory without backup. Never store initial link/token, temporary plaintext, external bearer tokens, screenshots, intent/clipboard data, drafts, or mutation queues. Maintain fixed HTTPS/host/port and HttpOnly/domain/path/expiration filters; bounded data and explicit versioning, failing closed on corruption.
2. Restore authentication on IO thread upon launch, verifying it strictly through native read-only catalog fetch. Do not auto-send messages, create chats, resume Agents, or decide approvals. Network unavailability does not wipe credentials; expired cookie / real 401 requires fresh login. Closing the transport must not be equivalent to forgetting saved login. No validity extension or changes to credentials/profile/backend/Tailscale in this task.
3. Provide explicit Log out / Forget local login action, without claiming remote revocation that DSH does not support. Preserve generation guards, nonce/preparation gate, UNKNOWN/SENDING ledger, noRetry, and retry prohibition. The ledger remains in RAM and there is no automatic draft restoration; do not attribute durability to unpersisted intents. Document the limitation of process termination with uncertain send, without restoring/retrying the intent.
4. Test storage/codec/boundary and lifecycle using JVM fixtures; test real Keystore on dedicated API 34 emulator with dummy data. Run protocol/app/lint/APK checks. Update README regarding persistent authentication and caveats. Do not install/update on personal phone, use Work profile, capture personal screen/logs, type private links, or alter backend TTL without separate authorization.

## Acceptance
Login securely stored encrypted and restored strictly for read-only operations; initial secret never persisted; native expiration/audience/auth intact; normal shutdown preserves login, Log out clears it; real Keystore tests and regression suite pass. Infinite validity is not promised: long-term server-side configuration remains a dedicated decision, potentially using 365 days or another finite duration. No published changes and no commit/push.
